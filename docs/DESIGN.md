Here we detail some key design decisions, which should be adhered to when designing new agents:

1. **Input Space Conventions** - Many design choices in the literature, such as the lengthscale hyperpriors in [Hvarfner et al. 2024](https://arxiv.org/pdf/2402.02229), have been tailored to domains which have been scaled to the unit hypercube `[0, 1]^D`. As such, the `Arena` has been written in such a way that agents are passed points, and should return points, in the unit hypercube. The `Arena` handles conversion *to* the unit hypercube when passing points to agents, and conversion *from* the unit hypercube to the original space when evaluating the given problem at the selected points.
2. **Acquisition Function Optimisation** - One of the aims of the BO Arena is to help to disentangle what is driving the performance of different agents in a controlled manner. As such, we have tried to standardise several choices for performing acquisition function optimisation, based on commonly used defaults in the literature. In particular, when using BoTorch's `optimize_acqf`, we use the following hyperparameters:
    - `raw_samples`: 5000 in total i.e. the number of points the acquisition function is initially queried at. Note that when `sample_around_best=True`, the effective number of `raw_samples` is twice that specified, hence why `raw_samples=2500` for agents such as `VanillaBO`.
    - `num_restarts`: 5 i.e. the number of gradient-based optimisation runs (typically done by L-BFGS-B) used to further refine the best of the `raw_samples`, for acquisition functions which are amenable to gradient-based optimisation (e.g. LogEI).

    Additionally, several other choices were introduced in [Vanilla BO, Hvarfner et al. 2024](https://arxiv.org/pdf/2402.02229), and were also adopted in the [Spherical Linear Agent, Doumont et al. 2026](https://arxiv.org/pdf/2512.00170). As such, we generally recommend following these settings too, and they can be found in the code for these agents. These settings result in a proportion of the `raw_samples` being sampled "closer" to the incumbent point(s) than they otherwise would be, and we refer to this approach as "BoTorch RAASP" in our paper (see Appendix B.1 for additional details). It should be noted that disabling these settings for Vanilla BO did not result in reduced performance on the problems used in our paper (see Figure 6).
